# Activation transaction boundary

Updated: 2026-10-03. Server-only Phase 1 primitives; no public enrollment endpoint, real activation page, verified device enrollment or session issuance is enabled. No hosted migration has been applied.

`server/activation-token.mjs` creates a 256-bit random bearer token with Node's cryptographic RNG and hashes decoded bytes with SHA-256. Only the digest belongs in `account_activations`. Tokens must use canonical base64url. Link generation requires a configured HTTPS chat origin without userinfo/path/query/fragment and puts the token in the fragment, which is not part of the HTTP request URL. This avoids placing it in ordinary request URLs but does not protect it from browser history, same-origin JavaScript or a compromised device. Future activation UI must clear the fragment promptly, avoid analytics/logging the token, and submit it only to the trusted activation endpoint. The utility does not share links or create an account by itself.

`issue_account_activation` requires a pending account, takes its row lock, loads positive integer `activation_ttl_seconds` from `app_settings`, revokes prior unused links and inserts the new digest/expiry. There is no policy default. TTL must fit PostgreSQL's integer seconds input; invalid/missing values fail closed. Account creation, max-user enforcement, authenticated admin step-up, audit actions and issuance rate limits belong to a future guarded endpoint, not this SQL function.

`complete_account_activation` looks up the digest, locks the account before the activation row, rechecks pending state, expiry, revocation and consumption, then inserts the first device, marks the account active and consumes the link in one transaction. Unknown/expired/revoked/replayed links use the same unavailable code. Device-key uniqueness failures roll back everything and leave the link unused. Both functions use invoker privileges, an empty search path and explicit service-role-only execution. Clients cannot read the activation table or invoke either function; forced RLS remains deny-by-default.

The caller must verify a fresh enrollment challenge, authentication credential and ownership of the supplied device signing key before completion. A public-key byte array is not proof of ownership. The service-role API bypasses RLS and is trusted backend authority, not an admin user token. These primitives do not enforce endpoint origin, admin session lifetime, WebAuthn verification or HTTP abuse controls and must not be exposed to anonymous requests as direct enrollment. Reactivation/history recovery is outside this increment.

The shared account-first lock order serializes issuing and completing a link. Expiry uses wall-clock `clock_timestamp()` after acquiring locks, so waiting inside a transaction does not extend validity. See [PostgreSQL row locks](https://www.postgresql.org/docs/17/explicit-locking.html#LOCKING-ROWS) and [current-time functions](https://www.postgresql.org/docs/17/functions-datetime.html#FUNCTIONS-DATETIME-CURRENT).

## Verification

`pnpm test:db` applies both migrations in the pinned, network-isolated disposable PostgreSQL fixture. The original account/device RLS suite remains passing. Activation tests cover missing policy, reissue revocation, successful atomic registration, replay, expired/unknown links, invalid input, duplicate-key rollback and denied client table/function access. Three independent races each use two concurrent database connections redeeming one token; exactly one commits and one fails, with a single device/consumed link/active account persisted.

`pnpm check` runs two new server utility tests along with the existing unit/infra checks: digest correspondence, independently generated tokens, fragment-only URLs, noncanonical token rejection and invalid origin rejection. No physical authenticator, signed JWT, Supabase/PostgREST integration, hosted activation UI, administrator authorization or phone enrollment test is claimed. Existing shell browser CI supplies the five-profile phase fallback coverage; Phase 1 is incomplete.

Next: server-verified passkey enrollment and challenge binding, device-key ownership proof and scoped session issuance, followed by a guarded activation endpoint/UI and physical iOS/Android tests. Do not enable real accounts before the crypto boundary and endpoint authorization gates pass.
