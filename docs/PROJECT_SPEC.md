# ACCOUNT MODEL: ADMIN-MANAGED (NO PUBLIC SIGN-UP)
- Public registration does NOT exist. Only admins create accounts.
- Super admin bootstrap: the first super admin is created ONLY via a CLI script (`pnpm admin:bootstrap`) that prints a one-time activation link; never through a web form. Script refuses to run if a super admin already exists (unless an explicit --force-recovery flag with confirmation is used, and that event is audit-logged).
- User creation flow:
  1. Admin enters username (+ optional display label, role, storage quota, feature flags) in the admin panel.
  2. Server creates the account with a random opaque ID and generates a SINGLE-USE, expiring (default 24h) activation link + QR. Only a hash of the token is stored.
  3. The user opens the link on their own device, chooses their passphrase and/or registers a passkey (WebAuthn). Keys (identity, prekeys) are generated ON THE USER'S DEVICE; only public keys are uploaded. The token is then consumed.
  4. Admin NEVER sees or sets the user's passphrase or private keys. Admin can never impersonate a user or log in as them.
- Account reset by admin = "re-activation": server wipes the account's public key material and sessions, issues a new activation link; the user creates NEW keys; all contacts see a "safety number changed" warning; old history is lost unless the user restored from their own recovery-phrase backup. Document this tradeoff honestly in THREAT_MODEL.md.
- Device linking requires approval from an existing logged-in device of the same user (QR). Admins cannot add devices to a user's account. Show the user a device list with a loud notification on every new device.
- Optional per-user first-contact policy (admin-configurable): users find each other via (a) shared org directory of usernames only, (b) invite links/QR only, or (c) both. No contact lists are uploaded to the server.
- Guests for anonymous rooms: only members can create anonymous rooms and invite guests via link; guests need no account (see section D).

# SUPER ADMIN PANEL (/admin, separate route group, same repo)
Roles: `super_admin`, `admin` (limited), plus regular `user`. Role changes only by super_admin.

Security of the panel itself:
- Mandatory WebAuthn (passkey) for all admin accounts; TOTP alone is insufficient and may only be additional verification; step-up re-authentication for sensitive actions (delete user, reset account, change role, change global settings).
- Stricter CSP than the user app, no third-party scripts, short session lifetime, optional IP allowlist via env var, strict rate limiting + lockout on failed logins.
- All admin actions go through Edge Functions using the service role; every action is checked server-side against the caller's role (never trust client-side role flags). RLS must also block admin roles from reading any ciphertext/envelope tables except what is strictly needed for delivery.
- Append-only, tamper-evident audit log (hash-chained rows) of all admin actions: who, what, target, timestamp. Admins cannot edit or delete audit rows. Viewable in the panel and exportable.
- Stretch: two-person approval for destructive actions (delete user, force-recovery).

Panel features:
- Users: create, list/search, view metadata (username, role, status, created_at, last_seen only if privacy-allowed, device count, storage used), suspend/unsuspend, delete (cascade ciphertext + blobs), re-activation/reset, regenerate activation link, set quota/feature flags, force-logout all sessions, revoke a specific device.
- Invitations/activations: list pending activation links, revoke, resend (new token).
- Groups/rooms: view only METADATA that the server legitimately has (opaque id, member count, created_at, expiry); cannot see names or content. Admin can disable/delete a group or room (ciphertext purge) and set global limits.
- Global settings: max group size, allowed message retention range, max file size, enable/disable calls, group calls, anonymous rooms, share links, scheduled messages, bulk-send rate limits; default privacy settings.
- Abuse & reports: inbox of user-submitted reports. Report content is decrypted client-side by the reporter, who explicitly picks messages, and re-encrypted to a dedicated admin "report key" (public key published by the server, private key held by super admin, rotatable). Admins see only what the reporter chose to send.
- System health dashboard: DB size, storage usage, realtime connections, error rates, failed jobs (pg_cron), TURN/LiveKit status. Zero content, zero IPs.
- Announcements: admin-signed system notices shown in the app (clearly labeled, signed so they cannot be spoofed by a user).
- Admin management: create/remove admins, rotate admin passkeys, view admin sessions.
- Panel is mobile-friendly with responsive tables (card layout on small screens).
- Be explicit in docs about what admins CAN see (metadata) versus CANNOT (content, keys).

# SECURITY ARCHITECTURE

## 1. Cryptography — use AUDITED libraries, do not invent primitives
- Target: 1:1 chats use the Signal protocol (X3DH/PQXDH + Double Ratchet) via the official `libsignal` Rust core compiled to WASM if feasible; groups use MLS (RFC 9420) via OpenMLS (WASM) or `ts-mls`.
- IMPORTANT: official libsignal has NO official browser build. Start with a time-boxed CRYPTO SPIKE (Phase 0.5):
  1. Try building libsignal's Rust core to WASM and run a full X3DH + Double Ratchet round trip in a browser Web Worker.
  2. Evaluate OpenMLS-WASM and ts-mls (maturity, maintenance, ciphersuites, API, bundle size, browser support).
  3. Evaluate using MLS for BOTH 1:1 (2-member group) and groups, so one audited protocol covers everything.
  4. Write docs/adr/0001-crypto-stack.md with the comparison and decision.
  5. If NO audited option works in the browser, STOP and ask me. Do not silently fall back to a hand-rolled protocol. Lower-level audited primitives (libsodium, @noble/*) are allowed only as building blocks, never to hand-roll a ratchet or group protocol.
- Keys: identity key, signed prekey, one-time (and post-quantum if supported) prekeys; only public parts go to the server. Private keys generated client-side, stored in IndexedDB as non-extractable CryptoKeys where possible and wrapped with a key from the user's passphrase (Argon2id WASM) or WebAuthn PRF/passkey.
- Media/files: client-side AES-256-GCM with a random key per file; only ciphertext in Supabase Storage; key travels inside the E2EE message. Encrypt file name/MIME/size; pad sizes.
- Message padding, authenticated associated data, replay protection.
- Safety numbers / QR verification, "verified" badge, loud warning on identity key change (including after admin-triggered re-activation).
- Opt-in encrypted backup: recovery phrase (BIP39-style) + Argon2id; server stores only the encrypted blob.
- Multi-device via QR with existing-device approval; device list; remote revoke (by user or admin).
- Local IndexedDB of decrypted messages encrypted at rest; app lock (PIN/biometric via WebAuthn) with auto-lock timeout.

## 2. Metadata minimization
- Sealed-sender style delivery where possible.
- No phone number or real email. Email recovery is deferred to the final phase. Leave a database/code extension point, but do not activate or require an email field now. Current account recovery uses only an admin-issued re-activation link.
- Random opaque IDs for users and conversations. No plaintext contact lists server-side.
- Web Push with no content ("New message" only).
- No IP logging in the app layer; document what Supabase/Netlify/coturn infrastructure still sees.

## 3. Web-specific trust hardening
- Strict CSP (no inline script/eval), Trusted Types, COOP/COEP, Referrer-Policy: no-referrer, Permissions-Policy, HSTS (production), SRI for any third-party script (prefer zero).
- Lockfile, `pnpm audit`, Renovate/Dependabot config, reproducible-build notes, published build hash, "app version / integrity" screen.
- THREAT_MODEL.md: honestly list what is and is NOT protected (malicious server/admin serving altered JS, compromised device, screenshots, traffic analysis, admin-triggered key resets).

## 4. Supabase security
- RLS on every table, deny-by-default, with policy tests (pgTAP/SQL scripts), including tests proving admin roles cannot read ciphertext or keys.
- Server stores only: public keys, ciphertext envelopes, encrypted blobs, opaque IDs, timestamps, delivery state, admin audit log.
- Rate limiting/abuse protection in Postgres/Edge Functions. Storage buckets private, short-lived signed URLs, ciphertext only.

# FEATURES

## A. Messaging
1:1 chats; groups (owner/admin/member roles, invite links, approval mode, max members configurable up to 1000 via admin settings); broadcast lists/channels; text, emoji, reactions, replies, forwarding (with "forwarding disabled" option), edit, delete-for-everyone, typing indicators, read receipts/ticks (optional), LOCAL-only search, client-side opt-in link previews, voice messages (waveform, 1x/1.5x/2x), images, video, files, GIFs (privacy-preserving or opt-in), location, contact cards, polls, stickers, drafts, @mentions, multi-select, unread jump, virtualized lists.

## B. Message controls
- Lock message / lock chat behind PIN/biometric (WebAuthn); locked chats excluded from notification previews and search.
- Self-destruct timers (5s, 30s, 1m, 1h, 1d, 1w, "after read"), per message and per chat; view-once media; clients enforce, server also purges ciphertext via pg_cron. Be honest that screenshots cannot be fully prevented.
- Share link: decryption key only in the URL fragment (#key) so the server never receives it; options: expiry, max views, optional password, revoke. Admin can globally disable the feature.
- Pin (messages and chats), star/favorites with filtered view.
- Archive, mute (timed), mark unread, labels/folders, wallpapers, themes (light/dark/AMOLED), font size, per-chat disappearing default.
- Block / report (see admin report flow).

## C. Scheduling and bulk
- Scheduled messages: client encrypts NOW, uploads ciphertext with `deliver_at`; pg_cron + Edge Function releases it at that time without ever seeing plaintext. Edit/cancel before delivery. Recurring option.
- Bulk send: select many contacts/groups; client encrypts a SEPARATE ciphertext per recipient; rate limited with progress UI. Broadcast lists where recipients don't see each other.
- Encrypted message templates / quick replies.

## D. Anonymous and ephemeral modes
- Anonymous private chat: created by a registered member via link/QR; guests need no account; random aliases; keys negotiated client-side; no history stored server-side; auto-destroys after TTL or when everyone leaves.
- Anonymous timed groups: mandatory expiry (1h–30d), random per-group aliases, no member list exposure, messages deleted at expiry, "burn room" button wipes for everyone.
- Per-chat alias/profile so identities are not linkable across chats.
- Tor/VPN-friendly (no IP-based fingerprinting in the app).
- Admin can enable/disable and set max TTL, but cannot read rooms.

## E. Voice & video calls
- 1:1 via WebRTC (DTLS-SRTP), signaling through Supabase Realtime with encrypted signaling messages.
- Group calls (up to 8 initially) via LiveKit SFU with E2EE (Insertable Streams / SFrame); keys distributed through the group E2EE channel.
- TURN: local coturn via Docker with short-lived credentials generated by a server-side API route; "privacy mode" forces relay-only.
- Features: mute, camera switch, screen share, speaker/earpiece toggle, picture-in-picture, client-side background blur, network quality indicator, ringing/missed calls/history, call banner, safety code on call screen.
- Mobile: wake lock, audio routing, backgrounding, permission prompts handled gracefully.

## F. Other
- Status/stories (24h, E2EE, selectable audience); encrypted Notes to self synced across linked devices; spaces/communities with sub-channels; granular last-seen/profile-photo privacy; blur on app switch; two-step verification, passkeys, session/device management; panic button (wipe local data); duress PIN (stretch).
- English-only UI with centralized text for future localization; no multilingual infrastructure for now. WCAG AA accessibility, keyboard navigation, reduced motion.
- Bots/webhooks OUT of scope for v1.
