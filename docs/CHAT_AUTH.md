# Chat authentication server boundary

Current continuation: see [DEVICE_ACTIVATION.md](DEVICE_ACTIVATION.md) for the application Worker, activation/login UI and complete browser test results. Earlier increment descriptions below are historical; hosted deployment and owner enrollment remain pending.

Updated 2026-10-03. This is a tested backend increment; Phase 1 remains incomplete. Routes require explicit `VAULT_AUTH_ENABLED=true`, a configured HTTPS `VAULT_CHAT_ORIGIN`, project URL and server API key. They return 503 while disabled. The chat activation/login UI and production encrypted-device Worker are not connected, hosted migrations are not applied, and no real account has been issued. Never enable this increment on its own.

The Next chat server exposes `/api/auth/activation-info`, `enroll-options`, `enroll-finish`, `login-options`, `login-finish`, `me` and `logout`. Only activation links issued by a trusted operator can enroll; there is no public sign-up, bootstrap or account creation HTTP endpoint. Every POST requires the configured exact origin; cross-origin Fetch Metadata is refused, including another same-site subdomain. No permissive CORS is sent. Credentials are verified with SimpleWebAuthn 14 against the stored random challenge, exact origin and hostname RP ID, with user presence/verification required. [The library documentation](https://simplewebauthn.dev/docs/packages/server) describes registration and assertion verification.

An HttpOnly, Secure, host-only, SameSite=Strict flow cookie binds each challenge to the initiating browser. A challenge is atomically taken before verification and cannot be retried after a bad signature, wrong origin, missing verification or other failure. Start again with fresh options. Expiry is checked again after transaction locks. Concurrent completion has exactly one winner.

Enrollment and login additionally require an Ed25519 signature from the registered OpenMLS device identity. The signed JSON tuple is `['vault-device-enrollment',1,canonicalDeviceIdentity,origin,challengeBytes,publicKeyBytes]`. This binds account/device IDs and the same 32-byte WebAuthn challenge; it is a device possession proof, not a new messaging protocol. Signing occurs through the OpenMLS identity's signer; the backend uses Node's standard Ed25519 verification. A synced passkey alone cannot log in as another device's private chat identity. Device linking and recovery are later work.

Successful verification invokes a service-only transaction committing activation, device, public KeyPackage, passkey and an opaque chat session together. Only public key material enters the server. KeyPackage bytes are stored with size bounds; this server increment does not parse or certify MLS KeyPackages. The production client and peers still need the audited core's validation and identity-directory checks. Encrypted local state must be durably saved before this finish call in the future UI.

Chat session cookies contain random 256-bit tokens; the database stores only SHA-256 digests, account/device/origin and expiry/revocation metadata. A device login fences its previous sessions. Session lookup rejects expiry, idle timeout, disabled accounts and revoked devices. Logout revokes the server record and clears cookies. An opaque session is not a Supabase Auth JWT or a decryption key; the existing authenticated RLS remains closed to it. Future delivery/Realtime authentication must explicitly bridge this boundary. There is no admin session issuer yet; the admin app remains a closed preview. An admin cookie cannot substitute for the chat cookie, and an admin origin cannot invoke this endpoint.

All seven auth/role/audit tables use forced RLS and revoke client and service-role direct access. The narrow security-definer RPC uses an empty search path and grants execution only to `service_role`; the public HTTP router never accepts arbitrary RPC actions. Global/account rate counts commit separately before credential verification, so failures cannot roll them back. Indexed cleanup deletes at most configured `auth_cleanup_rows_per_request` expired challenges and sessions per global rate check. Request streams and public-key/credential sizes are bounded by explicit settings. Unknown password, PRF and extension fields are refused; the future browser serializer must omit them completely, not send them for filtering. Errors disclose no SQL, secrets or project identifiers.

`account_roles` adds a normal user's extra role. A trigger rejects deleting/demoting the last super admin. Trusted operator bootstrap serializes account creation and writes a hash-chained audit of actions only. There are no role-edit HTTP endpoints. Future admin role changes still require fresh admin-origin passkey step-up and explicit self-demotion confirmation.

## Operator CLI

After the full client integration and hosted setup pass, use `pnpm auth:bootstrap bootstrap <settings.json> infra/runtime/first-admin.json`. Supply the configured server environment through your shell or Node `--env-file`; starting/building the app never runs bootstrap. Settings are required explicitly, with no production defaults. The first super admin gets an ordinary pending chat account and activation link. A second bootstrap is refused. `create-account` uses the same CLI as a trusted operator before the admin panel exists; it is not administrative session authorization.

The output must be a new file under ignored `infra/runtime`, created with mode 0600. The bearer URL is written before the database call so a lost response cannot discard the only local copy. The CLI refuses to overwrite a file and does not print the bearer token or key. Read and share the link yourself over your chosen private channel. `tests/auth/policy.json` is a test fixture, not a recommended production policy. This increment has no force recovery or public account reset; those cannot be improvised around the last-super-admin guard.

## Verification and remaining work

`pnpm test:auth` uses a disposable, network-isolated PostgreSQL 17 fixture and synthetic P-256 authenticators with real signatures. SimpleWebAuthn and the transaction/RPC implementation run unmocked. Ten scenarios cover successful registration/login, scoped cookies, session fencing/logout, missing UV, wrong origin/RP/challenge, invalid signature, stale counters, cookie binding, wrong device proof, concurrency, expiry, revocation, role invariants, audit chain, rate limits and missing policy. Concurrent super-admin demotions under repeatable-read isolation must leave at least one super admin. Fixture KeyPackages are arbitrary public bytes: these server tests do not claim a complete MLS enrollment flow, hosted PostgREST integration or hardware authenticator coverage.

Five additional browser cases verify the exact OpenMLS Ed25519 proof with Node crypto in Chromium, WebKit, Firefox, iOS emulation and Android emulation. The existing crypto regression matrix totals 84 cases. Physical phones still need the complete UI, Home Screen login, PRF/fallback, persistence and recovery tests. The owner's earlier iPhone result covers the shell only. Production Worker, activation/login screens, bootstrap on hosted Supabase and those complete cross-platform integration tests remain the Phase 1 completion gates.
